# Feature Specification: Catering Agent (`cater_agent`) Integration

**Feature Slug:** cater-agent-1788810577  
**Issue Type:** Product Specification / Feature Spec  
**Status:** CERTIFIED_APPROVED  
**Priority:** High  

---

## 1. Description & Context

**As a** Meeting Organizer planning team lunch meetings,  
**I want to** review three curated in-house catering menu options alongside proposed meeting time slots and select one to be saved with the meeting booking,  
**So that** team members have high-quality lunch catering arranged seamlessly as part of their meeting coordination workflow.

The Luncher orchestration system coordinates team lunch meetings across specialized agents (`strategy_agent`, `scheduling_agent`). This specification defines the integration of a new catering agent (`cater_agent`) under `@agents/`. Its purpose is to propose 3 curated menus sourced from the company's in-house catering service. For the initial version, `cater_agent` returns static mock menu suggestions without performing external database or inventory retrieval.

---

## 2. Key Product Decisions & User Feedback

The following product requirements and UX guardrails were established via user discovery and Spec Council review:

1. **Dedicated Catering Presentation Section**:
   - Catering menu options will be presented within a distinct, dedicated `### Catering Menu Options` section in the lunch proposal alongside meeting time slots and strategic rationale.
2. **Default Menu Fallback on Omission**:
   - If an organizer confirms a meeting time slot without specifying a catering menu, the system automatically defaults the selection to **Menu Option 1** (`menu_1`, Buffalo Chicken Wrap Platter) and records it in the booking record, ensuring smooth single-turn booking completion without conversational interruption.
3. **Warning & Automatic Fallback on Invalid Input**:
   - If an unrecognized or invalid menu choice is submitted (e.g., *"Book Slot 1 with Menu 4"*), the system warns the user that the selected menu is unrecognized, automatically falls back to **Menu Option 1**, and notes this fallback in the booking confirmation.
4. **Structured Menu Object Persistence**:
   - When a booking is finalized, the complete menu object—including the deterministic menu identifier, descriptive title, and full list of item strings—is saved directly in the meeting record (`catering_menu`), ensuring full downstream visibility for catering fulfillment.
5. **Static Mock Menus for Initial Version**:
   - The initial version strictly returns three fixed mock menus without external BigQuery/MCP querying or dynamic dietary filtering.
6. **Flexible Conversational Matching & Normalization**:
   - The conversational interface supports flexible natural language variations (e.g., *"Menu 2"*, *"Option 2"*, *"Veggie Tacos"*, *"the taco platter"*) and normalizes them to the target `menu_id` (`menu_2`). If the selection cannot be resolved to a known menu, the system triggers the standard warning and fallback to Menu Option 1.
7. **Session-Bound Identity & IDOR Prevention**:
   - The meeting booking process enforces cryptographic validation that the authenticated session identity matches the `organizer_id` in the booking payload, preventing Insecure Direct Object Reference (IDOR) vulnerabilities.
8. **Request Tracing & Orchestrator Rate Limiting**:
   - Orchestrated parallel sub-agent calls include a standard `correlation_id` header for distributed tracing. The planning and booking endpoints enforce rate limits to protect fan-out execution against resource exhaustion.

## 3. Business Context & User Workflows

### Target Personas
- **Meeting Organizer**: Plans team lunch meetings, reviews strategic context, team availability, and proposed catering menus, and locks in a final meeting time and meal.
- **Team Attendee**: Participates in the lunch meeting and benefits from curated, diverse catering options.
- **In-House Catering Coordinator**: Relies on persisted booking data to prepare and deliver the selected menu to the scheduled meeting room.

### Core User Journeys

#### Journey 1: Lunch Planning with Catering Options
1. The organizer asks the system to plan a lunch meeting (e.g., *"Plan a lunch meeting for the engineering team next Tuesday"*).
2. The orchestrator invokes `strategy_agent`, `scheduling_agent`, and `cater_agent` concurrently in parallel.
3. The system synthesizes a unified lunch proposal featuring:
   - Meeting title and strategic alignment rationale.
   - Team attendee roster and availability breakdown.
   - Ranked available time slots.
   - A dedicated **Catering Menu Options** section displaying all 3 mock menus with their items.
   - Guidance on how to confirm a time slot and catering menu.

#### Journey 2: Booking Confirmation with Explicit Catering Selection
1. The organizer responds with a selection specifying both slot and menu (e.g., *"Book Tuesday 12:00 with Menu 2"* or *"Book Tuesday noon with the veggie taco option"*).
2. The system normalizes the choice to `menu_2`, confirms the booking for Tuesday 12:00, records Menu Option 2 with all associated dishes in the meeting record, and returns a confirmation receipt.

#### Journey 3: Booking Confirmation with Default Menu Fallback
1. The organizer confirms only a time slot without specifying a menu (e.g., *"Book Slot 1"*).
2. The system confirms the slot and automatically defaults the catering selection to Menu Option 1 (`menu_1`), notifying the organizer in the confirmation response.

#### Journey 4: Booking with Invalid Menu Handling
1. The organizer specifies an invalid or unrecognized menu choice (e.g., *"Book Slot 1 with Menu 5"*).
2. The system issues a friendly warning about the unrecognized menu, falls back to Menu Option 1, completes the booking, and highlights the applied fallback.

#### Journey 5: Resilient Planning on Catering Degradation
1. The organizer requests a lunch plan when `cater_agent` is unavailable or times out.
2. The orchestrator gracefully proceeds using schedule and strategy outputs, including an informative notice that catering suggestions are temporarily unavailable, without failing the request.

## 4. Behavior-Driven Development (BDD) Acceptance Criteria

### AC1: Mock Catering Menu Output
```gherkin
Given cater_agent is initialized under @agents/
When cater_agent receives a menu proposal request for a lunch meeting
Then cater_agent returns exactly 3 mock menu suggestions:
  | Menu ID | Menu Name | Items |
  | menu_1  | Buffalo Chicken Wrap Platter | buffalo chicken wrap, mixed greens salad, chocolate cookie, assorted sodas |
  | menu_2  | Veggie Taco Fiesta | veggie tacos, snow pea salad, apple tartlets, tea service |
  | menu_3  | Indian Curry Feast | lamb vindaloo, spiced cauliflower, naan, orange-mint spa water |
And cater_agent does not execute any external network calls or database queries
```

### AC2: Parallel Sub-Agent Gathering & Context Isolation
```gherkin
Given luncher_agent receives a planning request from an organizer
When luncher_agent triggers its information gathering phase
Then luncher_agent invokes strategy_agent, scheduling_agent, and cater_agent concurrently in parallel
And context isolation ensures no attendee PII or extraneous scheduling context leaks into cater_agent
And all sub-agent invocations pass a common correlation_id for distributed telemetry
And total gathering duration is bounded by max(strategy_latency, scheduling_latency, catering_latency)
```

### AC3: Proposal Synthesis with Catering Section
```gherkin
Given strategy_agent, scheduling_agent, and cater_agent have returned their respective planning data
When the proposal synthesizer constructs the final lunch proposal
Then the output contains a distinct "### Catering Menu Options" section
And each of the 3 mock menus is listed with its descriptive title and individual course items
And the proposal provides clear instructions on selecting a preferred menu during booking confirmation
```

### AC4: Booking Confirmation with Conversational Menu Matching
```gherkin
Given a lunch proposal containing the 3 catering options has been presented
When the user submits a confirmation matching either an explicit ID ("Menu 2") or descriptive phrase ("Veggie Tacos")
Then the system normalizes the selection to menu_2
And creates and persists a meeting booking record containing:
  - time_slot: "Tuesday 12:00-13:00"
  - catering_menu.menu_id: "menu_2"
  - catering_menu.name: "Veggie Taco Fiesta"
  - catering_menu.items: ["veggie tacos", "snow pea salad", "apple tartlets", "tea service"]
And the system returns a confirmation message detailing the confirmed time and selected menu
```

### AC5: Booking Confirmation with Default Menu Fallback
```gherkin
Given a lunch proposal containing the 3 catering options has been presented
When the user submits a confirmation specifying "Book Slot 1" without referencing catering
Then the system creates and persists a meeting booking record containing:
  - time_slot matching Slot 1
  - catering_menu.menu_id: "menu_1"
  - catering_menu.name: "Buffalo Chicken Wrap Platter"
  - catering_menu.items: ["buffalo chicken wrap", "mixed greens salad", "chocolate cookie", "assorted sodas"]
And the confirmation response indicates that Menu Option 1 was selected by default
```

### AC6: Handling Invalid Catering Selection with Warning and Fallback
```gherkin
Given a lunch proposal containing the 3 catering options has been presented
When the user submits a confirmation specifying an unrecognized menu (e.g., "Book Slot 1 with Menu 4")
Then the system records the booking using Menu Option 1
And the confirmation response alerts the organizer that the choice was unrecognized and Menu Option 1 has been assigned
```

### AC7: Graceful Degradation on Catering Sub-Agent Failure
```gherkin
Given cater_agent encounters an internal error or exceeds the 5.0 second gather timeout
When luncher_agent gathers data for a planning request
Then proposal synthesis completes successfully using outputs from strategy_agent and scheduling_agent
And the proposal includes proposed time slots and strategic rationale
And the proposal includes a user-facing notice that catering suggestions are temporarily unavailable
```

### AC8: Session-Bound Authorization & Ownership Validation
```gherkin
Given an authenticated user submits a booking confirmation request
When the booking record is constructed
Then the system validates that the authenticated session identity matches the organizer_id
And rejects the booking attempt if a cross-user identity mismatch is detected
```

## 6. Constraints, Boundaries & Out of Scope

### In-Scope
- Creation of `cater_agent` returning the 3 prescribed mock menus.
- Parallel fan-out gathering alongside `strategy_agent` and `scheduling_agent`.
- Proposal synthesis integrating the dedicated `### Catering Menu Options` section.
- Saving selected `catering_menu` object inside the meeting `BookingRecord`.
- Conversational fuzzy menu matching with normalization to canonical `menu_id`.
- Defaulting to `menu_1` when the organizer confirms a slot without menu selection.
- Warning and fallback to `menu_1` when an unrecognized menu selection is provided.
- Session authorization validating `organizer_id` to prevent IDOR attacks.
- Graceful degradation when `cater_agent` is unavailable or times out.

### Out of Scope
- Direct queries to BigQuery, external catering vendor APIs, or MCP servers (reserved for future iterations).
- Individual attendee dietary restriction polling, allergen tagging, or customized dish swaps.
- Payment processing, billing allocation, or expense ledger recording.
- Catering order cancellation or modification after initial booking confirmation.

### Non-Functional Requirements (NFRs)
- **Response Latency**: `cater_agent` response time < 50ms locally.
- **Gathering Timeout**: Orchestrator sub-agent call timeout set to 5.0 seconds.
- **Context Isolation & Privacy**: Organizers' attendee lists and personal identifiers must not be forwarded to `cater_agent`.
- **Distributed Tracing**: All parallel sub-agent requests must propagate a `correlation_id` header.
- **Abuse Prevention**: Rate limits enforced on planning and booking endpoints to prevent fan-out resource exhaustion.
- **Accessibility & Screen Readers**: Proposal markdown headers must follow standard H2/H3 semantic hierarchy (`### Catering Menu Options`) for screen reader navigability.
